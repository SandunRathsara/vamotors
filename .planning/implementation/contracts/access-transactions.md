# Actor, authorization, atomicity and observable transport

## A1: trusted actor and multirole grants

Server-created context only: `{kind:'USER',userId,sessionId,requestId,loadedAt,authzRevision,grants}` or `{kind:'SYSTEM',scope:'RESERVATION_EXPIRY',runId,requestId}` or `{kind:'IMPORT',initiatedByUserId,batchId,requestId}`. Never accept actor/rules/requester/reviewer fields from body. Session authenticates identity, NOT activation/grants. HTTP, RSC/server reads, export, file access, import and scheduled entry use same policy seam. Load current User.active/UserRole/RolePermission every request; request-local reuse only. Command rechecks authority inside transaction. Revocation committed before the command's authorization lock wins; an already linearized transaction may finish. Role changes and protected commands serialize on relevant auth rows/guard; no request-start snapshot may authorize a later execution after revocation commits.

Default deny; effective grants are UNION of all current role positive grants. V1 role editor stores grants only, not CASL `cannot`/inverted rule priority (which could accidentally subtract another role's grants). System constraints (self-review, append-only, last admin, environment) always deny independently; Administrator cannot override them. Supported actions/subjects/field names have a server registry; arbitrary strings in `Grant.subject` are validated against it. Allowed condition keys only `createdBy`, `customerId`, `financeCompanyId`, `status`, `recipientUserId`, equality only; `$actor.id` substituted server-side. No raw Mongo operators/JavaScript/SQL, unbounded nested predicates or client permission payload evaluation. Unknown conditions fail role save `422 INVALID_INPUT`.

Instantiate actual record subjects for CASL checks; type-only `can('update','SaleCase')` is UI hint, never authorization. Write: check action, actual record and EVERY requested changed field including nested paths; forbidden field → `403 FIELD_FORBIDDEN`, never silently remove it and return misleading success. Derived inputs (price, consideration, finance fields) require their own field permission and command capability. Create checks candidate subject with server-controlled ownership fields. Cannot change ownership solely to make conditions match. Default capability mapping: `create` for create/initiate/record commands; `update` for edits/resolution/return/complete; `pay` for receipts/refunds/reversals; `dispatch`, `reconcile`, `approve`, `run`, `import` for corresponding commands. Composite commands require all participating capabilities (e.g. trade-in intake needs purchase create, sale complete needs cycle update + payment create). Review commands recheck both domain capability and approval permission as A4 specifies.

Read: scope rows BEFORE total count/sort/pagination, then project permitted fields from actual subjects. Allowlisted simple conditions compile to parameterized SQL; unsupported query condition fails closed, never fetch-all then page-filter. Every output branch, nested relation, aggregate, export and audit diff gets its own field checks. Aggregate of forbidden inputs is forbidden too; omit financial object/totals with `redactedFields`, not zero (zero implies real data). For filtering/sorting by forbidden field return `403 FIELD_FORBIDDEN`, not an inference oracle. Hidden row returns404 even when guessed ID exists. Nested links require target read; display unavailable label if source allowed but target denied. Notifications contain no price/name/private document material that could leak after target permission revoked; authorize link target again on click. No initial list permission implies access to all records.

**Concrete field scenario:** roleSales grants read Vehicle `{id,identity,status,available,cycleId,revision}`; roleFinance grants read Vehicle `{financial,listedPrice}` condition createdBy=$actor.id. Combined actor sees financial fields only on own vehicle. Other vehicle JSON/CSV/PDF/audit excludes financial and does not sort by listedPrice. Adding finance role broadens union; revoking it next request removes fields even with same session/browser cache. Purge client private query cache on logout/401/403/authzRevision change; never embed raw DB entity in hydration props. UI permission copies are hints, never a second authority.

Admin mutations lock singleton AdminGuard then account/role rows in sorted ID order. Count distinct active users with protected Administrator role, not number of assignments. Reject removal/deactivation of final active admin (`409 LAST_ADMIN`); protected system role cannot archive/rename/remove systemKey (`409 SYSTEM_ROLE_PROTECTED`). Concurrent removals: first may pass, second recomputes and fails. Runtime cannot directly bypass guarded role writes; T03 DB trigger proves direct write invariant. Active Administrator remains seeded with account/role management grants; attempted removal of final admin's administrative authority blocked too.

Current CASL docs checked via ctx7 `/stalniy/casl` on 2026-10-25: `guide/restricting-fields` demonstrates instance vs type checks and `permittedFieldsOf(...,{fieldsFrom})`; `api/casl-ability-extra` describes `rulesToQuery`. T03 must pin/verify the chosen package API; no dependency installation/API adapter was made in T01. Use explicit registry fieldsFrom; absent fields does not mean return entire database object.

### A1F: field registry naming

Subject names are the closed `Subject` union in api.ts. Permission field paths use **wire/business names**, not raw SQL column names; normalize actual row to authorization subject before evaluating. `SaleCase.price` maps agreedPrice, `Vehicle.financial` maps its cycle projection, `createdBy` is immutable persisted creation actor (never browser input). Allowed read field universe for Vehicle/SaleCase/Customer/BrokerageDeal is the corresponding DTO's declared keys and nested leaf paths; operational write field universe is exactly the named command input keys for that subject, excluding server actor/ID/revision and immutable source fields. `fields:['*']` explicitly expands to that subject/action universe, `fields:[]` grants no fields, omitted fields rejected on role save. No implicit all-field grant from a missing array. Compound fields financial/payments/finance/tradeIn/quote/guarantors/checklist authorize the entire subtree only when explicitly granted; leaf-only grants cannot accidentally include sibling values.

Concrete sensitive paths: Vehicle `listedPrice`, `financial.purchase`, `financial.repairs`, `financial.additionalCosts`, `financial.basis`, `financial.originalProfit`, `financial.restatedProfit`; SaleCase `price`, `payments`, `finance.down`, `finance.principal`, `finance.lenderOutstanding`, `tradeIn.value`; BrokerageDeal `quote`, `approvedLoan`, `processingFee`, `facility`; Customer identity/address/phone/email/licence; Document attachment byte capability; AuditLog each diff path inherits its original entity's read-field grant in addition to audit-read. Approval payload inherits original domain field checks, not a broad approval inbox leak. Read restriction may recursively omit these declared fields (`Visible<T>`); list/page envelopes always retain counts/timestamps/redaction metadata. A report whose primary measure cannot be read returns403 rather than an empty/misleading financial report; nonfinancial inventory may omit its financial object/totals. Record-grant conditions are evaluated on trusted row properties even when those properties themselves are hidden in output. Server registry tests must assert unknown subject/path/operator fails closed and every DTO sensitive field has a mapping.

## A2: transaction and audit boundary

One command owns one transaction; subdomain functions accept caller tx, never start independent commits. Pipeline: authenticate/current activation → strict bounded input validation and coarse action guard → acquire current auth locks and idempotency/cycle/source locks → actual record/field authorization → current revision/state/date/obligation/approval validation → business+payment+status history+audit+required recipient notifications+CommandReceipt → commit → minimized response. Never external R2/PDF/network inside tx. Essential-write failure (even audit or notification FK failure) rolls back EVERYTHING, including idempotency claim. Queries and prevalidation cannot authorize later effects without recheck.

Isolation: serializable interactive transaction or equivalent explicit locks + all constraints, verified with real driver in T03. Lock order: E5X BusinessSequence guard for report-affecting mutations → AdminGuard/auth rows → normalized identity advisory locks sorted engine/chassis pair (for new identities) → existing Vehicle IDs sorted → cycle IDs sorted → SaleCase/reservation/approval → finance company → remittances sorted → entitlements sorted. All participating flows use same order; do not lock approval first then cycle in reviewer. Read proposal dependencies before tx to plan locks, then reread under locks. Foreign/key uniqueness failures map to named conflicts, not500. Expected revisions are compare-and-set and increment once per aggregate per command; dependent child changes increment parent. Revenue/cost-affecting changes also increment cycle/sale revision. Max revision2^31-1 rejects `REVISION_EXHAUSTED`, never wraps. Export source-version writes are essential in caller tx and rollback with audit/business/payment rows; snapshot cutoff acquires/releases same sequence guard to avoid a partial committed prefix.

Audit entry per changed entity, field-level before/after (create from null, archive active true→false, status explicit); both actedBy and requestedBy/approver as appropriate. Money canonical strings, instants UTC, reason1..2000 trimmed characters. Hashes/passwords/tokens/session cookies/signed URLs/secret env are excluded; account create audit includes account ID/email/roles only, never credential. Auth login/logout events may be separate security logs, not business field history. No user/API including admin may update/delete audit. Runtime grants INSERT/SELECT only on audit; update/delete trigger rejects even accidental grants. Migration owner privileges are operationally separate, not a claim of tamper-proofness against a DB owner.

Notifications: five required kinds, immutable eventKey `domain:event:sourceId:version`, recipient-specific unique key, mutable readAt only by recipient. Approaching/expired recipients: active users with read Reservation + update/complete reservation capability; repair return: active users with read cycle and release/repair capability; approval-required: active nonrequester with applicable approve capability; outcome: requester. Optional configured subscriptions may narrow but cannot remove mandatory requester/outcome and applicable reviewer routing. Snapshot recipient list in tx; no recipient lookup after response. No eligible reviewer → `409 OBLIGATION_OPEN` with safe message “configure a separate reviewer”, not silently orphan request. Reviewer may later lose authority, requiring reassignment/current inbox query; notification never conveys authority. Mark-all uses server-clamped `through<=now` so notifications arriving later stay unread. Duplicate jobs never duplicate notifications. Polling sufficient; no queue/SSE infrastructure required.

## A3: HTTP, retries, idempotency, revisions

Commands `POST /api/v1/commands/{name}` with exact `Envelope<Commands[name]>` from api.ts. Same-origin credentials; reject untrusted Origin on cookie-auth mutations, including multipart; require CSRF protection appropriate to selected auth integration. JSON schemaVersion=1; max command body1MiB (import upload separate), all strings length1..2000 except name<=200, identity<=100, reference<=200, emails<=254; business input arrays default<=100 unless documented50 dispatch/200 total import rows/9 photos; Envelope.expected allows<=1000 distinct dependency references (e.g. multiple parents for200 import rows or50 dispatch members), no duplicate authority shortcut. Unknown fields rejected; optional omitted vs explicit null only where type permits. Password never echoed/audited. Lists read-only GET `/api/v1/queries/{name}` with validated URL params; complex compare/report filters may POST to `/api/v1/queries/{name}` (no writes, still auth/CSRF). All protected responses `Cache-Control: private,no-store`; static public assets only service-worker cache.

Required expected dependencies are exhaustively specified by `commandRevisionRules` in api.ts and A3R below, including child-owner resolution. Missing any required revision →428 REVISION_REQUIRED; mismatched authorized entity →409 STALE_REVISION with current references only (no forbidden fields). Client refetches/retains form and explicitly reconfirms with new key, never silently retries changed input/revision. Supplied extraneous dependencies cannot authorize anything; mismatching duplicate(type,id) entries422 INVALID_INPUT. All resolved required dependencies must be authorized before revealing revision errors.

### A3R: authoritative revision selectors and child bumps (finding1)

The typed `commandRevisionRules` object has one entry for **every** Commands key (compile-time exhaustive). `Type:input.path` means that exact current row, UUID taken from validated input; arrays are handled only by the named expansion below. `@` expansions are **server** FK queries, never browser-supplied owner claims; reread/lock them in the same transaction as CAS. Every distinct required(type,id) appears once in expected with its current revision, including immutable RateSheet/Quote revision1. Current read DTOs expose those IDs/revisions. New children have no expected revision until created, but their existing authoritative parents do. Optional expansion returns [] only where explicitly allowed here; missing required child/target404, never silently an empty expansion.

### A1Q: safe administrative reads (finding2)

`currentActor` is authenticated self-only; deactivated session403, no session cookie/token/password/hash/account rows in DTO. Its opaque authzRevision fingerprints current activation + user assignment revision + sorted role IDs/revisions/rules, computed per request; it is a cache invalidation hint, never authorization. presentationGrants only that actor's own effective grants, no other users' rules; roles are own IDs/names. Change fingerprint clears all private client caches and refetches. `users/user` require current User.read on scoped rows AND each returned name/email/active/roles/adminProtection field; `roles/role` require Role.read (including grants field separately); assigned-user counts are absent unless actor can read whole count population. Last-admin status only for authorized user administrators. `permissionRegistry` exposes validated action/subject/field/condition grammar, no DB secrets; Role.read+Role.update or User administration capability required, registry filtered to subjects/fields the actor is allowed to configure. Role editor still cannot confer authority through a read response. All lists/detail enforce row scope before pagination and no-store. Self currentActor is not permission to list accounts. QueryResponse Visible projections and redactedFields apply, credential fields never exist even for Administrator.

Idempotency key UUID generated once per intended user action and retained across timeout/network retry. Scope `(environment,authenticated actorKey,commandName,key)`; hash canonical validated envelope (including schema and expected revisions), sorted object keys, ordered arrays retained, undefined absent; do not hash raw JSON whitespace. Store safe committed response reference/hash atomically. Same key+same input → same command/result identifiers and replayed=true; SAME key+different input →409 IDEMPOTENCY_MISMATCH. Reauthorize replay against **current** activation/record/fields; never leak saved payload after revocation. Response serialization projects current allowed fields but cannot create new effects. Pending approval receipt always returns same proposal even if later approved; UI queries proposal/outcome. InitUpload replay does not create another slot; if old PUT expired return UPLOAD_EXPIRED, new key required. Committed receipts retained indefinitely. Password-bearing create hashes use keyed server digest of validated request; do not persist plaintext password in input/hash diagnostics.

Concurrent identical key: lock/unique serializes; winner commits, loser reads receipt. If bounded wait exceeded →409 COMMAND_IN_PROGRESS, retryable with retryAfterMs1000. Winner rollback leaves no receipt, retry may execute once. Network lost after commit: retry same key or permissioned commandStatus returns committed result, never invent another payment. Internal transaction retries max3 total attempts, jitter/backoff within host budget, same key, only serialization/deadlock transient errors; no external side effects. Exhausted →503 RETRYABLE_TRANSACTION + Retry-After1. Client retries GET/transient503/429 only (same key for commands); never automatic retry 403/409 stale/422. Nonessential invoice generation has its own key, cannot roll back or repeat sale.

## A4: four approvals — exact payload, not generic patch

`requestApproval` stores typed Proposal, schemaVersion1, exact command input, all expected dependencies and server current listed/terms/basis snapshots, requester/reason/time, canonical SHA256 hash. Proposal dependencies include cycle, vehicle identity, sale/reservation, relevant policy/company and original payment IDs/revisions. Pending has no sale, cash, mileage, stock hold or domain effect. Discount reserve/startFinance must approve before receiving deposit/creating commitment too: frontend must label funds “not yet recorded” while pending. Rejection leaves original state and retained user form; no phantom refund.

`reviewApproval` locks dependencies in A2 order and proposal row, rechecks PENDING/revision/hash and current reviewer active grants on exact record AND domain action/fields. Reviewer!=requester unconditionally. No Administrator bypass, no client reviewer ID, no editable proposal. Revalidate requester remains active and still has originating domain authority (otherwise stale); current reviewer authority cannot rely on old notification/session. Decision approve executes stored owner command under caller tx with approval context; business effects, approved status, appliedCommandId, audit and outcome notification commit together. No “approved now, execute arbitrary payload later” window. Stale dependencies →409 APPROVAL_STALE; transaction may separately mark STALE+audit+outcome only, no partial domain writes. Rejection requires nonblank note, records reviewer/time once; exactly same-key replay returns prior result, a new competing review key →409 ALREADY_REVIEWED. A second approval does not override first.

| Proposal | Payload and safeguards |
| --- | --- |
| DISCOUNT | Exact completeImmediate/placeReservation/startFinance command, cycle+listed revision, price/customer/date/payment/trade-in; discount amount=list-price minus price, never subtract twice. Changing asking price/customer/date/amount invalidates proposal. No reserve while pending. |
| WRITE_OFF | Exact WriteOff date/reason/method/proceeds+receipt, basis/cycle revision. Open repair/commitment blocks; zero explicit. Approval executes disposal/close/payment atomically. |
| REFUND | Exact Refund amount/date/method/remainder/disposition + original receipt/reservation revision. 0<refund<=unrefunded advance; retainedAmount=advance-refunds. Approved cancellation ends commitment even partial; remainder explicitly retained, stock disposition mandatory. |
| SALE_EDIT | Exact SaleEdit whitelist, completion/current correction/basis revision, reason and explicit payment corrections. Immutable identity/cycle/payment history cannot be changed by patch; original snapshots/PDFs retained. Price change on lease must keep down+finance balance; price below committed cash requires explicit difference correction, never implicit refund. |

SaleEdit whitelist is concrete in api.ts (customer/price/reference/date/mileage/notes, finance terms/DO, trade-in description/value); immutable sale kind/cycle binding cannot be reassigned. Method/date/amount corrections go through explicit cashCorrections. Repair/cycle/customer-identity corrections use their owner commands. Finance-company corrections revalidate policy/DO/company links and existing entitlements/allocations; reverse allocations first or fail OBLIGATION_OPEN, never silently move reconciled money between companies. Trade-in value corrections with an acquired cycle require that cycle still open/no resale, reasoned linked basis restatement in same tx; otherwise OBLIGATION_OPEN with separate controlled correction required. No unrestricted JSON object copied into DB. Payments on completed sale cannot be mutated through generic reversePayment: require SALE_EDIT approval if changing its consideration/received facts; later legitimate lender receipt uses recordLenderReceipt, not sale edit. Purchase/cost reasoned restatements do not alter original snapshot; reports expose revised profit explicitly. Any correction blocked by outstanding allocation/obligation returns OBLIGATION_OPEN with actionable resolution, not silent waiver.
