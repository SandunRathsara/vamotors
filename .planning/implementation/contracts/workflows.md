# Lane command/query contracts

All commands use api.ts envelope, A1–A4 authorization/transaction/retry rules, M1–M3 money/date rules, E1–E6 relations. Success means durable APPLIED/result reference/affected revisions, not local state only. `nextActions` comes from server state + actor capabilities; no placeholder “next step” replaces a callable command. Any unspecified mutation is rejected, never handled through a generic status setter.

## W04: parties, customer and settings (T04)

create/updateCustomer validates every required/optional field from CustomerInput; normalized identity match conflicts instead of duplicate. create/updateDirectoryParty supports individual/company suppliers/vendors, multiple full contacts, primary marker and specialisation/recurring/notes; create/updateFinanceCompany stores shared policy version. Archive/reactivate preserves historical FKs; archived entities cannot be selected for new business (`409 INVALID_STATE`), but old attachments/sales remain readable under grants. Contact archive cannot invalidate old verification snapshots. Inline pickers run persisted directory create commands with their own retained key and invalidate party/customer queries; selecting a just-created entity works in purchase/sale/brokerage. Required phone nonempty and syntactically plausible (3..30 chars, no external validation), email optional valid syntax, no guess at NIC checksum; unique normalized NIC/passport prevents accidental duplicates, manual correction reason required.

Customer detail returns fields + all linked buyer SaleCases AND customer-as-seller trade-in acquisitions, with IDs/dates/type/status and permission-projected amounts. Search q matches normalized full/calling name, identity or phone, never in-browser fixture joins. Party list tab type is a server filter. Settings saves immutable version after validating contiguous tier coverage, bounded leadDays/processingFee, dealership identity/declarations/theme/items/date format; money/currency snapshots unchanged historically. No currency conversion/multi-currency feature. Empty list results differ from denied request; invalid settings422 field errors.

## W05: purchase/availability (T05)

recordPurchase creates or reuses normalized engine+chassis identity under sorted identity lock; if existing details conflict return IDENTITY_CONFLICT with authorized record reference, not silently overwrite physical fields. Existing open cycle conflicts; previous SOLD is repurchasable, WRITTEN_OFF is not ordinary stock. supplier must be active, BRAND_NEW company only. Supplier cash/brand-new price>0 records actual full PurchasePayment at purchaseDate (these input channels describe paid purchases); settlement total computed as institution+seller, >0, both >=0, emits only positive actual payment components. `payPurchase` is for outstanding historically imported/corrected partial liabilities, capped by remaining component; cannot pay already full acquisition again. Institution company ID mandatory for FINANCE_COMPANY, BANK/PRIVATE_PARTY explicit name, reference required. Initial mileage can be0; vin/cr optional. Receipt/receiveStock not implicit: newly acquired cycle PURCHASED unavailable until explicit physical receipt. UI may offer “save and receive” only as two explicit commands, not hide Purchased history.

editPurchase requires reason for any field; changes price/settlement validate totals and explicit cashCorrections, never rewrite old payments. Before close update basis; after close append CycleBasisVersion restatement and preserve original completed profit. editVehicle requires reason, collision check, cannot silently merge identities; snapshot invoices unaffected. setListedPrice before close independent cost; changes cycle revision and invalidates pending discount proposal (active advance retains listed snapshot). addMileage append-only; decreasing reading requires reason. addCost amount>=0/description/date/category, optional actual payment<=cost; edits require reason and cash correction if amount below paid. receiveStock requires date and disposition; HOLD requires reason, RELEASE only after all guards. sendRepair may start from held IN_STOCK, cannot start while committed. Failures include STOCK_UNAVAILABLE, IDENTITY_CONFLICT, OBLIGATION_OPEN, BALANCE_MISMATCH, STALE_REVISION,422 bad dates; no partial identity/cycle/payment on audit failure.

## W08: repairs/disposal (T08)

sendRepair persists vendor/request/sentDate + IN_REPAIR/unavailable in same tx, one open repair. returnRepair requires actual invoice>=0/date/return/summary, no stored estimates, return>=sent; adds actual cost even unpaid and held stock + required return notifications. `payment?` records actual amount/date only; payRepair partials capped invoice, paidAt independent. History is chronological across cycles with each cycle linkage visible, not replacement of old repair. Disposal requires A4 WRITE_OFF proposal, explicit reason/date/method/proceeds0 allowed, no outstanding repair or buyer obligations; snapshot basis, close cycle WRITTEN_OFF. Positive proceeds require matching actual receipt, zero creates none. Rejection leaves status unchanged because pending never changed it. NetLoss=basis-proceeds can be negative if recovery exceeds basis, labelled gain rather than silently clamped. Refusing unresolved obligations is not disabled write-off: return repair/cancel reservation then make fresh proposal.

## W09/W10: all four sale categories, reservation, lease (T09/T10)

completeImmediate accepts CASH or TRADE_IN. Requires available IN_STOCK, active customer, positive price, date<=today, mileage>=0, optional reference. Cash residual computed, not trusted input; exact full receipt/method + completion/mileage/closed cycle/status/audit atomic. If listedPrice null no discount threshold; positive listed price recommended, required for reservation. Below-listed routes to pending approval, with no receipt/completion. TradeIn.value positive<=price; descriptive-only no inventory; supplied intake creates full new cycle/customer seller in same tx. Same physical identity as sold vehicle fails IDENTITY_CONFLICT; cannot take currently owned identity into stock twice. Combined finance+trade-in absent from v1 UI, not approximated.

placeReservation: amount>0<=agreed, listed>0; snapshot tier/price/timezone/lead; receipt date placement, commit SaleCase+Reservation+receipt+ADVANCE_PLACED/unavailable. Below-listed agreed price gated before any receipt. Multiple unresolved attempts prohibited incl EXPIRED. convertReservation on ACTIVE or EXPIRED same customer, agreed terms, exact balance=agreed−net advance credit (only unresolved reservation, no prior cancelled remainder). balance0 → null/no zero receipt. At due instant late cron does not block conversion of expired reservation; writes effective expired event before resolution if necessary in same tx. Complete handover/sale/mileage once. Cancellation before OR after expiry supported: cancelRetained requires retainedAmount=net advance, reason, explicit RELEASE/HOLD; refund proposal amount0<refund<=net advance with retained remainder. Refund cancellation is full termination, not an extension/partial live reservation. Original +100/-60 remains,40 retained. No refund needed for no-refund cancel. No extension endpoint, no duplicate advance “replacement.”

startFinance: positive down/finance, term1..120, down+finance=price, active company, snapshot path/commission policy and price approval. Records down receipt once and FINANCE_PENDING; cannot start on another customer's reservation by bypass. recordDO: complete verified target-bound DO attachment+issueDate, sets DO_RECEIVED with no cash or delivery. confirmDOAndHandover atomically completion+mileage+SOLD and commission entitlement, not lender receipt. Company terms/selected policy snapshot survive later edits, but current permissions and DO ownership checked. RecordLenderReceipt accepts partial actual amounts<=outstanding principal on actual date, later than handover allowed; bank transfer expected, CASH requires explicit company collection reference. Example down100 on Jan1, DOJan3, handoverJan4, lender900 Jan8 → cash100 Jan1 +900 Jan8 only, consideration1000 Jan4.

`reversePayment` is a reasoned correction capability, not money deletion: exact opposite + replacement, source lock and cumulative validation, with sale-completion correction routed to SALE_EDIT approval. Active commitments with corrected credit must still satisfy terms; otherwise OBLIGATION_OPEN until an exact refund/cancel proposal or correction resolves. No generic finance cancellation button: erroneous finance initiation correction requires A4 SALE_EDIT-equivalent protected proposal using explicit reversal+release payload, specified below, rather than silent resets.

### W10C: correcting an erroneous uncompleted finance case

To avoid an unresolvable entered-in-error commitment, the SALE_EDIT proposal additionally accepts `CANCEL_FINANCE_ERROR` with `{saleCaseId,reason,receiptReversals:[paymentId],disposition}`. Allowed FINANCE_PENDING/DO_RECEIVED only, no completion/entitlement/lender receipts, all down-payment facts reversed as accounting corrections with actual dates unchanged, no claim of a physical customer refund. Actual return of customer money must be a separately dated refund proposal with amount/method/date and linked original down receipt; same REFUND kind accepts finance case target, capped net receipts, and cancels only when all down consideration resolved. These are correction/refund safety seams, not a new ordinary sale type or automatic abandonment. Exact version + separate reviewer required; DO evidence retained, state CANCELLED, cycle IN_STOCK explicit disposition. Requests claiming money never existed versus money actually refunded must be visibly distinct. Outstanding lender receipts/completed case must use completed sale correction, never this route.

### W12F: facility payout AND recovery
