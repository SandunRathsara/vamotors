# Lane command/query contracts

All commands use api.ts envelope, A1–A4 authorization/transaction/retry rules, M1–M3 money/date rules, E1–E6 relations. Success means durable APPLIED/result reference/affected revisions, not local state only. `nextActions` comes from server state + actor capabilities; no placeholder “next step” replaces a callable command. Any unspecified mutation is rejected, never handled through a generic status setter.

## W04: parties, customer and settings (T04)

create/updateCustomer validates every required/optional field from CustomerInput; normalized identity match conflicts instead of duplicate. create/updateDirectoryParty supports individual/company suppliers/vendors, multiple full contacts, primary marker and specialisation/recurring/notes; create/updateFinanceCompany stores shared policy version. Archive/reactivate preserves historical FKs; archived entities cannot be selected for new business (`409 INVALID_STATE`), but old attachments/sales remain readable under grants. Contact archive cannot invalidate old verification snapshots. Inline pickers run persisted directory create commands with their own retained key and invalidate party/customer queries; selecting a just-created entity works in purchase/sale/brokerage. Required phone nonempty and syntactically plausible (3..30 chars, no external validation), email optional valid syntax, no guess at NIC checksum; unique normalized NIC/passport prevents accidental duplicates, manual correction reason required.

Customer detail returns fields + all linked buyer SaleCases AND customer-as-seller trade-in acquisitions, with IDs/dates/type/status and permission-projected amounts. Search q matches normalized full/calling name, identity or phone, never in-browser fixture joins. Party list tab type is a server filter. Settings saves immutable version after validating contiguous tier coverage, bounded leadDays/processingFee, dealership identity/declarations/theme/items/date format; money/currency snapshots unchanged historically. No currency conversion/multi-currency feature. Empty list results differ from denied request; invalid settings422 field errors.

## W08: repairs/disposal (T08)

sendRepair persists vendor/request/sentDate + IN_REPAIR/unavailable in same tx, one open repair. returnRepair requires actual invoice>=0/date/return/summary, no stored estimates, return>=sent; adds actual cost even unpaid and held stock + required return notifications. `payment?` records actual amount/date only; payRepair partials capped invoice, paidAt independent. History is chronological across cycles with each cycle linkage visible, not replacement of old repair. Disposal requires A4 WRITE_OFF proposal, explicit reason/date/method/proceeds0 allowed, no outstanding repair or buyer obligations; snapshot basis, close cycle WRITTEN_OFF. Positive proceeds require matching actual receipt, zero creates none. Rejection leaves status unchanged because pending never changed it. NetLoss=basis-proceeds can be negative if recovery exceeds basis, labelled gain rather than silently clamped. Refusing unresolved obligations is not disabled write-off: return repair/cancel reservation then make fresh proposal.

### W10C: correcting an erroneous uncompleted finance case

To avoid an unresolvable entered-in-error commitment, the SALE_EDIT proposal additionally accepts `CANCEL_FINANCE_ERROR` with `{saleCaseId,reason,receiptReversals:[paymentId],disposition}`. Allowed FINANCE_PENDING/DO_RECEIVED only, no completion/entitlement/lender receipts, all down-payment facts reversed as accounting corrections with actual dates unchanged, no claim of a physical customer refund. Actual return of customer money must be a separately dated refund proposal with amount/method/date and linked original down receipt; same REFUND kind accepts finance case target, capped net receipts, and cancels only when all down consideration resolved. These are correction/refund safety seams, not a new ordinary sale type or automatic abandonment. Exact version + separate reviewer required; DO evidence retained, state CANCELLED, cycle IN_STOCK explicit disposition. Requests claiming money never existed versus money actually refunded must be visibly distinct. Outstanding lender receipts/completed case must use completed sale correction, never this route.

## W16: historical import (T16)
